# Combining tables — JOINs & set operators

<Accroche>« Data lives in separate tables on purpose; **joins** put it back together on demand. »</Accroche>

## Intuition

A well-designed database splits data across tables to avoid repetition: customers in one
table, their orders in another, linked by a **key** (`orders.customer_id` points at
`customers.customer_id`). A **JOIN** recombines them row by row when you need the whole
picture. **Set operators** (`UNION`, `INTERSECT`, `EXCEPT`) instead stack the *results* of
two queries vertically.

<SqlSchema />

## Syntax

### Joins

```sql
-- INNER JOIN: only rows that match in BOTH tables
SELECT o.order_id, c.first_name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;

-- LEFT JOIN: every row from the left table, NULLs where the right has no match
SELECT c.first_name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- RIGHT JOIN / FULL OUTER JOIN: mirror of LEFT / both sides kept
-- CROSS JOIN: every combination of rows (Cartesian product)
```

`JOIN` on its own means `INNER JOIN`. SQLite has supported `RIGHT` and `FULL OUTER JOIN`
since version 3.39 (this engine is newer, so they work here). A **self-join** joins a table
to itself — useful for hierarchies like employees and their managers.

### Set operators

```sql
SELECT name FROM products WHERE category_id = 1
UNION
SELECT name FROM products WHERE category_id = 2;   -- distinct rows from either
```

`UNION` removes duplicates (and sorts); `UNION ALL` keeps every row (and is faster).
`INTERSECT` keeps rows in **both** results; `EXCEPT` keeps rows in the first but **not** the
second. The two `SELECT`s must return the same number of columns. (Some databases spell
`EXCEPT` as `MINUS`.)

## Common pitfalls

<Pitfall>

**An `INNER JOIN` silently drops unmatched rows.** If you join customers to orders with a
plain `JOIN`, customers who never ordered simply vanish from the result. When you need to
keep them (and reveal the gaps), use `LEFT JOIN` — the missing side comes back as `NULL`.

</Pitfall>

<Pitfall>

**`UNION` is not the same as `UNION ALL`.** `UNION` removes duplicate rows (extra work);
`UNION ALL` keeps every row, including duplicates, and is faster. Use `UNION ALL` unless you
specifically want de-duplication. Also: both `SELECT`s must have the same number of columns.

</Pitfall>

## Mini-exercises

<Collapsible title="Q: What is the difference between JOIN and CROSS JOIN?">

A `JOIN … ON` keeps only rows where the condition matches. A `CROSS JOIN` has no condition
— it pairs **every** row of the left table with **every** row of the right (the Cartesian
product), so 10 customers × 13 products = 130 rows.

</Collapsible>

<Collapsible title="Q: What does INTERSECT return?">

Only the rows that appear in **both** result sets. For example,
`SELECT country FROM customers INTERSECT SELECT country FROM customers WHERE signup_date >= '2024-01-01'`
returns countries that have at least one 2024 sign-up.

</Collapsible>

<Collapsible title="Q: Why give the same table two aliases in a self-join?">

So you can refer to the two "copies" separately. In `employees e JOIN employees m`, `e` is
the employee and `m` is the manager — without the aliases, SQL couldn't tell which
`first_name` you meant.

</Collapsible>
