# Pruebas (testing)

<Accroche>« Código sin pruebas es código que crees que funciona. Con pruebas, lo sabes — y tu juego no se rompe al añadir un enemigo nuevo. »</Accroche>

Escribir **pruebas** es comprobar automáticamente que tu código hace lo que esperas. Te da confianza
para cambiar cosas sin miedo: si algo se rompe (el cálculo del daño, la detección de colisiones), una
prueba te avisa al instante.

## `assert` — la prueba más simple

`assert condicion` no hace nada si la condición es verdadera, y **lanza un error** si es falsa. Es la
base de todas las pruebas:

```python
def daño_critico(x):
    return x * 2

assert daño_critico(3) == 6
assert daño_critico(0) == 0
print("Todas las pruebas pasaron")
```

Si alguna afirmación fallara, el programa se detendría con un `AssertionError`.

## Una tabla de casos

Un patrón muy práctico: una lista de `(entrada, resultado_esperado)` y un bucle que las comprueba. Por
ejemplo, la función que decide si un enemigo sigue vivo:

```python
def esta_vivo(hp):
    return hp > 0

casos = [(30, True), (0, False), (12, True)]
for entrada, esperado in casos:
    assert esta_vivo(entrada) == esperado
print(f"{len(casos)} pruebas OK")
```

## `unittest` — el marco de pruebas estándar

Para proyectos de verdad, Python trae `unittest`. Agrupas las pruebas en una clase y usas métodos
como `assertEqual`. Ejecuta esto y mira el informe:

<PyExercise
  task="Ejecuta esta batería de pruebas del cálculo de daño con unittest y observa el informe. (Se ejecuta igual en tu máquina.)"
  starter={`import unittest

def daño(a, b):
    return a + b

class TestDaño(unittest.TestCase):
    def test_positivos(self):
        self.assertEqual(daño(2, 3), 5)
    def test_cero(self):
        self.assertEqual(daño(0, 0), 0)

unittest.main(argv=["", "-v"], exit=False)`}
/>

<Pitfall>
Prueba también los **casos límite**, no solo el camino feliz: la lista vacía, el 0 de vida, un daño
negativo, una entrada inesperada. Ahí es donde se esconden la mayoría de los errores.
</Pitfall>

## Mini-ejercicios

<Collapsible title="1. ¿Qué es TDD (desarrollo guiado por pruebas)?">

Escribir la **prueba primero** (que falla porque aún no hay código), luego el código mínimo para que
pase, y después limpiar. El ciclo *rojo → verde → refactor*. Ayuda a diseñar y a no romper lo que ya
funciona.

</Collapsible>

<Collapsible title="2. En proyectos reales, ¿unittest o pytest?">

Ambos valen. `unittest` viene incluido; `pytest` (se instala aparte con `pip install pytest`) es más
conciso: te deja usar `assert` normal y descubre las pruebas solo. Muchos proyectos usan `pytest`.

</Collapsible>
