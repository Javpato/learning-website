# Prepare Your Big Project

<Accroche>« Before building something ambitious, lay the foundations: structure, environment and the ideas of movement. »</Accroche>

The final project is a **platformer** with graphics. This chapter prepares you for it: how to organize a
big project across several files, how to set up the environment, and —most importantly— the **movement
logic** (gravity, jumps, collisions), which you can understand in pure Python before touching graphics.

## A project in several files

Big programs are split into **modules**, each with one responsibility:

```text
mini-plataformas/
├── main.py         # starts the game and holds the main loop
├── settings.py     # constants: screen size, gravity, colors
├── player.py       # the Player class (movement, jump, drawing)
├── level.py        # the level: platforms, coins, enemies
├── assets/         # images and sounds
└── README.md
```

Each file imports what it needs: `from settings import GRAVEDAD`, `from player import Player`.

## Virtual environment and dependencies

To install libraries without polluting your system, you use a **virtual environment**:

```bash
python -m venv venv           # create the environment
source venv/bin/activate      # activate it (Windows: venv\Scripts\activate)
pip install pygame            # install Pygame inside the environment
pip freeze > requirements.txt # save the dependencies
```

Whoever clones your repo can reinstall everything with `pip install -r requirements.txt`.

## The physics of movement

A falling character has a **position** (`y`) and a **vertical velocity** (`vy`). At each step of the
game, gravity increases the velocity, and the velocity moves the position. You can simulate it without
graphics:

```python
y = 0
vy = 0
gravedad = 1
for paso in range(4):
    vy += gravedad     # gravity accelerates the fall
    y += vy            # velocity moves the character
    print(y)
```

## Collision with the ground

A character doesn't fall forever: when it reaches the ground, it **stays** there. That's a simple
collision: if the position goes past the ground, it's clamped to the ground.

```python
def limitar_al_suelo(y, suelo):
    if y > suelo:
        return suelo      # touched the ground: it stays on it
    return y
```

<Pitfall>
In a game, **first** you update all the positions (physics), **then** you check collisions and correct,
and **last** you draw. If you mix the order, the character "jitters" or goes through the platforms. That
order — move, resolve, draw — is the heart of the game loop.
</Pitfall>

## A good README and version control

Before publishing: write a clear `README.md` (what it is, how to run it, screenshots) and make small,
frequent commits with `git`. A tidy history is also part of a good project.

## Mini-exercises

<Collapsible title="1. What does the velocity vy represent in a jump?">

When you jump, you give `vy` a large **negative** value (upward, because on screen y grows downward).
Gravity keeps adding to it each step, so it goes up, slows down, and falls again: a parabola. Exactly
what you did in the first exercise, but starting upward.

</Collapsible>

<Collapsible title="2. Why separate settings.py?">

Because having the constants (size, gravity, colors) in one place lets you **tune the game** without
hunting for magic numbers all over the code. You change the gravity on one line and the whole game feels
it.

</Collapsible>
